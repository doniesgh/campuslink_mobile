# Deploying CampusPulse

How the API runs online and how a new APK is published for the team. To run the project on your own machine, see [how-to-run.md](how-to-run.md) instead.

| Part | Where | Cost |
|---|---|---|
| API | [Render](https://render.com) web service `campuspulse-api`, Frankfurt, defined by [`render.yaml`](../render.yaml): **https://campuspulse-api-fmbf.onrender.com/api** | free |
| Database | [MongoDB Atlas](https://www.mongodb.com/atlas) M0 cluster, database `campuspulse` | free |
| Push notifications | Firebase project `com-example-campuspulse` | free |
| APK | GitHub Releases of this repository | free |

---

## 1. The database (MongoDB Atlas), once

**Already have a cluster for another app?** Reuse it: one cluster holds several databases. Atlas allows only one free cluster per project anyway.
- **Use the database `campuspulse`.** MongoDB creates it on the first write. The other app keeps its own database, and our `seed` only touches `campuspulse`.
- **Give CampusPulse its own database user,** limited to its database:
  - In **Database Access**, choose **Add New Database User** and set a password.
  - Under **Database User Privileges**, choose **Grant specific privileges** and add **`readWrite`** on database **`campuspulse`**.
  - Then neither app can read or break the other's data, even with a wrong address or a leaked password.
- **Network Access** probably already has `0.0.0.0/0` if the other app runs on Render. Add it otherwise.
- **Limits:** both apps share the free cluster's 512 MB and its connection limit. CampusPulse's data is tiny.

Then go straight to steps 4 and 5 below, with the new user.

To start from nothing instead:

1. **Create a free cluster:** on cloud.mongodb.com, choose **Create › M0 (free)**, region **Frankfurt** (close to Render's).
2. **Create a user:** in **Database Access**, add a database user with a password and the role *Read and write to any database*.
3. **Open the network:** in **Network Access**, add `0.0.0.0/0`. Render's free plan has no fixed IP address, so the user and password are what protect the database.
4. **Copy the address:**
   1. On cloud.mongodb.com, open the project, then **Clusters**, and click **Connect** on the cluster.
   2. Choose **Drivers**, Node.js. Copy the string:
      ```
      mongodb+srv://<db_username>:<db_password>@cluster0.abcde.mongodb.net/?retryWrites=true&w=majority&appName=Cluster0
      ```
   3. Replace **`<db_username>`** and **`<db_password>`**, brackets included, with the CampusPulse user and its password.
   4. Add **`campuspulse`** after `.mongodb.net/`:
      ```
      mongodb+srv://campuspulse:S3cretPass@cluster0.abcde.mongodb.net/campuspulse?retryWrites=true&w=majority&appName=Cluster0
      ```
   A password with `@ : / ? # [ ] %` must be URL-encoded. It's simpler to give the user an autogenerated password, which has only letters and digits.

   This is a secret: it goes into Render, and nowhere in the repository.
5. **Test it from your PC before using it.** In PowerShell:
   ```powershell
   cd backend
   $env:MONGO_URL = "<the address>"
   npm run db:check
   Remove-Item Env:MONGO_URL
   ```
   It must end with `OK: signed in, and this user can write to this database.` Otherwise it says what to fix: the password, the network access, or the host.

## 2. The API (Render), once

1. On dashboard.render.com, choose **New › Blueprint**, connect GitHub and pick **this repository**. Render reads `render.yaml`.
2. Fill in the values it asks for:
   - **`MONGO_URL`**: the Atlas address above.
   - **`MAIL_RELAY_URL`, `MAIL_RELAY_SECRET`, `SMTP_*`** (optional): real emails for sign-up codes and password resets. Leave them empty for now (see [Emails](#emails-sign-up-codes-and-password-resets) below): the codes are then printed in Render's **Logs**.

   Click **Apply**. Render generates `JWT_ACCESS_SECRET` itself.
3. **Push notifications:**
   - Open the service, then **Environment › Secret Files › Add Secret File**.
   - Name it **`firebase-service-account.json`**, and paste the content of `backend/firebase-service-account.json`.
   - Save. Render redeploys.
4. **Check it:** the **Logs** must show `[push] On: …`, `[push] Class reminders on: …` and `CampusPulse API listening …`. Then open `https://<your-service>.onrender.com/api/health`. It must answer `{"status":"ok"}`.

Every push to `main` redeploys the API (`autoDeploy`).

### Demo data in the cloud database

From your PC, point the backend scripts at Atlas for one command. In **PowerShell**:

```powershell
cd backend
$env:MONGO_URL = "<the Atlas address>"
npm run seed
npm run create-admin -- admin@campus.test "<a new admin password>"
Remove-Item Env:MONGO_URL
```

- **`seed`** creates the demo accounts and the data of every screen. **Running it again resets them**, so everything teammates changed in the demo data is lost.
- **`create-admin`** gives the demo admin a new password. The default one is written in this repository, so anyone could otherwise manage the users. Share the new one only with the team.

### Emails: sign-up codes and password resets

Without email settings, the API prints the codes in Render's **Logs**. Teammates then can't verify a new account themselves, and an admin has to create their accounts.

**Render's free plan blocks the usual email ports** (25, 465, 587), so Gmail's SMTP can't work there. Instead, the API sends through **Gmail with a small Google Apps Script**, which it calls over HTTPS. The emails come from your Gmail address, up to **100 a day**.

1. **Make a secret** (any 16+ characters, shared by the API and the script):
   ```bash
   node -e "console.log(require('crypto').randomBytes(24).toString('base64url'))"
   ```
2. **Create the script:**
   - Go to [script.google.com](https://script.google.com), signed in with the Gmail that will send.
   - Click **New project**, name it `CampusPulse mail relay`, and replace the content of `Code.gs` with [`backend/mail-relay/gmail-relay.gs`](../backend/mail-relay/gmail-relay.gs). Save.
3. **Give it the secret:** in **Project Settings** (the gear icon) › **Script Properties**, choose **Add script property**, with property `SECRET` and value the secret. Save.
4. **Deploy it:**
   - Choose **Deploy › New deployment**, then the gear next to *Select type* › **Web app**.
   - Set **Execute as: Me** and **Who has access: Anyone**, then click **Deploy**.
   - **Authorize access:** pick your account. Google warns that the app isn't verified, because it's your own script: choose **Advanced › Go to CampusPulse mail relay**, then **Allow** (it asks to send email as you).
   - Copy the **Web app URL**, which ends with `/exec`. Opening it in a browser shows `{"ok":true,"service":"CampusPulse mail relay",…}`.
5. **Test from your PC first.** Add to `backend/.env`:
   ```
   MAIL_RELAY_URL=<the Web app URL>
   MAIL_RELAY_SECRET=<the secret>
   SMTP_FROM=CampusPulse <your Gmail address>
   ```
   Then run `cd backend && npm run mail:test`. It must end with `Sent to … through the Gmail relay`, and the email arrives from your Gmail (check the spam folder). Otherwise it says what to fix.
   - The relay replaces SMTP when both are set.
   - `SMTP_FROM` only gives the sender name and the test's default recipient.
6. **Put them on Render:** in the service's **Environment**, set `MAIL_RELAY_URL`, `MAIL_RELAY_SECRET` and `SMTP_FROM` to the same values, then **Save, rebuild and deploy**.
7. **Check it** by registering in the app with a real address: the code arrives by email.

If you change the script later, choose **Deploy › Manage deployments ›** ✏️ **› Version: New version › Deploy**. The URL stays the same.

#### Or: Brevo

[Brevo](https://www.brevo.com) is free for 300 emails a day and accepts SMTP on port **2525**, which Render doesn't block. It needs no script, but you need a Brevo account.

1. **Sign up** on brevo.com, free plan.
2. **Verify a sender:** in **Settings › Senders, Domains & Dedicated IPs › Senders › Add a sender**, enter the name `CampusPulse` and the address the emails come from (e.g. your Gmail). Confirm with the code Brevo emails you.
3. **Get the SMTP login:** in **Settings › SMTP & API › SMTP**, note the **Login** (like `9a1b2c001@smtp-brevo.com`), then click **Generate a new SMTP key** and copy it. It is shown only once.
4. **Test from your PC first**, with the same values in `backend/.env`:
   ```
   SMTP_HOST=smtp-relay.brevo.com
   SMTP_PORT=2525
   SMTP_USER=<the SMTP login>
   SMTP_PASS=<the SMTP key>
   SMTP_FROM=CampusPulse <the verified sender address>
   ```
   Then run `cd backend && npm run mail:test -- <your address>`. It must end with `Sent to …`, and the email arrives (check the spam folder). Otherwise it says what to fix.
5. **Put them on Render:** in the service's **Environment**, set `SMTP_HOST`, `SMTP_USER`, `SMTP_PASS` and `SMTP_FROM` to the same values (`SMTP_PORT` is already `2525`), then **Save, rebuild and deploy**.
6. **Check it** by registering in the app with a real address: the code arrives by email.

### The free plan sleeps: UptimeRobot keeps it awake

After 15 minutes without requests, Render stops the API:
- The next request then takes up to a minute.
- **Class reminders don't go out while it sleeps.**

A free [UptimeRobot](https://uptimerobot.com) monitor calls the API every few minutes, so it never sleeps. It also emails you when the API is down.

1. **Sign up** on uptimerobot.com (free plan) and confirm your email.
2. Click **New monitor** and fill in:

   | Field | Value |
   |---|---|
   | Monitor type | **HTTP(s)** |
   | URL | **`https://campuspulse-api-fmbf.onrender.com/api/health`** |
   | Friendly name | `CampusPulse API` |
   | Monitoring interval | **5 minutes** (anything up to 10 is fine: Render sleeps after 15) |
   | Alert contacts | your email |

3. Click **Create monitor**. Within a few minutes it shows **Up**, with response times under a second once Render is awake.

**Optional: a status page for the team.** In **Status pages › New status page**, add the monitor. Share the link, so teammates can see whether the API is up before blaming the app.

**Render's free hours:** a workspace gets **750 free instance hours a month**, and one service awake all month uses about 720. If another free service in the same Render workspace (e.g. another app's API) is kept awake too, together they run out before the month ends, and Render suspends them until the next month. Keep only one awake, or move one to a paid plan.

## 3. Building the APK

### The signing key

Every APK we give out must be signed with **the same key**, otherwise it can't update the app already installed (teammates would have to uninstall first).

- The key is `android/campuspulse-release.jks`, and its passwords are in `android/key.properties`. Both are gitignored.
- **Keep a copy of both files** somewhere private, such as your own Drive. If they are lost, the next APK needs a new key and everyone reinstalls.
- Without `key.properties`, a release build is signed with the debug key. That's fine to try on your own phone, but don't publish it.

### Build

1. Check that **`env/prod.json`** has the Render address: `"API_BASE_URL": "https://<your-service>.onrender.com/api"`.
2. Put the Firebase file **`android/app/google-services.json`** in place, otherwise push is off in the APK.
3. Raise **`version`** in `pubspec.yaml` for every new APK: `1.0.0+1`, then `1.0.1+2`, and so on. The number after `+` must always go up, or Android refuses the update.
4. Build:
   ```bash
   flutter build apk --release --dart-define-from-file=env/prod.json
   ```
   The APK is `build/app/outputs/flutter-apk/app-release.apk` (about 57 MB, for every phone). Rename it `campuspulse-<version>.apk`.
5. **Try it** on your own phone, or on the emulator by dragging the file onto it. Sign in with the demo student, and check that the data loads.

## 4. Publishing it (GitHub Release)

1. On the repository's GitHub page, choose **Releases › Draft a new release**.
2. Create the tag **`v<version>`**, e.g. `v1.0.0`, on `main`, with the title **`CampusPulse <version>`**.
3. Describe what changed, and add the install steps below.
4. **Attach** `campuspulse-<version>.apk` and click **Publish release**.

### Installing it (for teammates)

1. On the phone, open the release page and download `campuspulse-<version>.apk`.
2. Open the downloaded file. Android asks to allow **installing unknown apps** from the browser or the Files app: allow it, then tap **Install**.
3. Sign in with the demo student or your own account. Tap **Allow** for notifications to get the class reminders.

Later versions install over the old one the same way, and the data is kept.
